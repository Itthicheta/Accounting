# Mamapook Accounting Mock App — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A deployable SPA where accounting staff can upload the Grab merchant export (per-branch reconcile + performance dashboard) and enter Catering/Event revenue — the two modules usable today — persisting to the Supabase `acc` schema.

**Architecture:** Vite + React + TypeScript SPA, no server. Grab xlsx parsed client-side (SheetJS); all pure money-math in `src/lib/*` modules with vitest tests; persistence via supabase-js pinned to the `acc` schema; auth = Supabase email/password (staff accounts created by admin; public signups stay disabled). Deploys as static files to Cloudflare Pages.

**Tech Stack:** Vite 7, React 19, TypeScript, react-router-dom 7, @supabase/supabase-js 2, xlsx (SheetJS), vitest.

## Global Constraints

- Supabase project `xnmzlqqudizckjhchhpn`, schema **`acc`** only (exposed via PostgREST; anon has zero grants — every query needs an authenticated session).
- Repo is **public**: no bank account numbers, no real business data, no secrets in code or fixtures. Branch/bank mapping lives only in `acc.branches`. `VITE_SUPABASE_URL` + `VITE_SUPABASE_KEY` (publishable key) via `.env` — safe for client, still gitignored.
- Thai labels appear in UI copy where staff-facing (branch names come from DB).
- Grab parsing must key on **หมวดหมู่ + payout id** (never Auto/Manually-Paid keywords); GF order codes are unique only per **branch+date**.
- Money: parse to JS number, round display to 2dp, compare with tolerance 0.01.
